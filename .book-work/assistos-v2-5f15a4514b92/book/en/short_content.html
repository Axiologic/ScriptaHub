AssistOS

Second edition · A ten-minute reading

A workplace for delegated work

AssistOS begins with an everyday problem: a person can ask an AI system for help, but the work still has to live somewhere. Files change, tasks continue after a conversation ends, people review results, and permissions must survive changes in tools. The second edition presents AssistOS as an operating layer for this continuing collaboration. Its ambition is an integrated workplace for documents, research, programming, administration and creative projects, where people delegate useful tasks and retain control of the outcome.

This is a product and research direction, supported by existing building blocks. The book describes the intended integrated experience; actual functionality depends on the packages and integrations in a particular installation. Its central claim is architectural: dependable assistance requires project continuity, explicit authority and inspectable results alongside capable models. A fluent answer alone does not establish that useful work has been completed.

Begin with one assignment

A good first task is bounded and reviewable. A software team might ask for a small repository change with tests. A researcher might ask for a comparison of supplied papers, with citations linked to the underlying evidence. Someone preparing a document might request a revision that preserves the source and exposes the differences. The assignment identifies the relevant files, expected output, acceptance criteria and actions that require approval. A vague instruction to improve everything gives neither the worker nor the reviewer a useful boundary.

A Robot is the persistent virtual worker to which the person delegates. It has a role, configuration, permitted resources, task history and a private execution environment. An AI Agent is the reasoning-and-action software it uses. A Ploinky Agent is an installable capability package, which may contain an AI Agent, deterministic tools, a service or a complete application. Keeping these three meanings separate makes it possible to change the underlying model or software without erasing the worker’s identity.

Keep conversation, files and decisions together

Explorer is the shared workspace for projects, files, tools and Robots. WebChat is the conversational Copilot and dispatch interface. WebMeet brings people and visible Robot participants into meetings around shared work. A team might ask a Robot to retrieve evidence or propose a document change during a meeting, then inspect the result together. The important connection is between the conversation and the object being changed, rather than merely adding an automated voice to a call.

The project is the durable container for work. Source documents, proposed revisions, accepted versions and derived results need distinct identities. A proposal should not silently become the authoritative document. Task histories connect outputs with inputs, decisions and the capability versions used. Version control supports code review; document comparison supports editorial review; evidence and citations support research review. Plugins can provide the appropriate editor or visual interface while preserving the common project context.

Supervise work while it happens

Delegation does not require continuous conversation. A Robot can perform a background task while the person works elsewhere, then return with a concrete result. Useful status describes the work: reading inputs, running tests, awaiting approval, retrying after a dependency failure, or ready for review. The user should be able to interrupt, redirect or stop the task. Observability means recording meaningful actions and outputs, not exposing private internal reasoning.

Browser automation makes this especially tangible. A Robot can navigate an administrative application, collect information or prepare a form, while the user watches the browser and takes over when needed. Multifactor authentication, hardware security keys, legal consent and consequential submissions can remain human steps. A persistent browser profile is sensitive state because cookies can carry authenticated authority. It needs isolation, controlled access and a revocation path, rather than casual sharing between workers.

Turn good results into repeatable procedures

A successful task can become a reusable procedure with stages, required inputs, tools, checkpoints and acceptance conditions. The procedure preserves more than the wording of a prompt: it records how a result is produced and checked. Failures and human corrections help identify missing constraints or weak steps. Improvement should be judged by repeated performance, review effort and recovery, rather than by how convincing a single demonstration appears.

Autonomy can grow selectively. Observation allows analysis without changes. Proposal mode produces revisions or planned actions for review. Bounded execution permits well-understood operations. Some tasks can eventually run in the background without continuous supervision. These levels need not apply equally to every action: a Robot might work freely in a test environment while remaining restricted in production. Approval should occur at meaningful boundaries, such as publishing, spending money or making an irreversible change, so users are not trained to confirm every harmless operation mechanically.

Make authority explicit and recovery practical

An execution boundary controls what software can affect. Containers and lighter sandboxes help isolate commands and dependencies, but isolation alone is not a complete authorization policy. Least privilege limits access to the files, devices, network destinations and identities needed for the task. Dedicated service accounts and scoped API tokens distinguish Robot actions from human actions. Secret management should provide only the required credentials to the appropriate environment; unrelated secrets should never become ordinary agent context.

Failure modes include prompt injection through untrusted content, hallucinated assumptions, tool misuse, compromised dependencies, changing website interfaces, provider outages and uncontrolled cost. Responses include narrow tool contracts, evidence requirements, deterministic validation, package provenance, budgets and visible failure states. Reversible work offers better recovery: reject a proposed revision, restore a document version or discard a code branch. Sending a message or completing an external transaction may not be reversible, which makes approval before execution more important.

Package capabilities and preserve useful state

A model cannot supply an entire working environment by itself. Programming needs compilers, repository tools, package managers and tests. Research can require PDF extraction, citation databases and retrieval tools. Data work may need database drivers, Python libraries and visualization software. Ploinky packages declare runtimes, dependencies, startup commands and interfaces, making these capabilities installable and versioned. A capability that starts successfully still needs functional and security evaluation before people rely on its advertised behavior.

Different tools should retain suitable interfaces. MCP supports discovery and structured tool calls. OpenAI-compatible APIs can expose model-like services. Command-line interfaces remain useful for mature developer tools, and web applications can retain valuable visual interfaces. Adapters and compatibility tests are necessary because protocols and versions differ in practice. A Robot’s persistent home keeps role configuration and selected application state, while project outputs remain in project folders. Caches should be rebuildable, credentials revocable and execution environments replaceable without destroying useful work.

Choose where computation runs

Local-first does not mean local-only. A laptop may handle extraction, indexing or a small model; a private server may support a team; a remote model may be justified for difficult reasoning. Placement should follow the dependencies of the entire task. A background task on a laptop cannot continue after shutdown unless execution is transferred or restarted elsewhere. Local preprocessing can select relevant information before a remote call, but privacy depends on the actual data flow and must be checked.

The book connects sovereignty with concrete choices: data location, model provider, private deployment, exportable projects and traceable procedures. Models can change while the work remains. A practical continuity test replaces the model or restores the project elsewhere, then checks whether source files, accepted versions, criteria and previous results remain usable. Exporting documents without procedures, permissions or dependency information preserves only part of the work. Portability also has limits when licensed datasets or hosted integrations cannot move unchanged.

Build trust before a marketplace

Organizations add governance around the same Robot model: approved capability catalogs, identity, access rules, secret handling, audit records and spending limits. Central administration can coexist with execution on approved local machines or private servers. A useful catalog explains the outcome a capability supports, its required resources, permissions, interfaces, evaluations, maintainer and update policy. Thousands of poorly described packages would reproduce the integration problem rather than solve it.

The commercial sequence follows demonstrated utility. Establish a few reliable workflows, make installations repeatable, then offer managed deployment, support, private catalogs or specialized distributions. Measure accepted tasks, human correction time, errors, recovery and cost. Open source can support inspection and provider choice, but demand and operational reliability still need evidence. Competition from large platforms, security failures, complexity and weak product focus remain substantial risks.

Keep research accountable to real tasks

The research program explores ways to combine learned models with explicit computation. Conventional software can check fields, calculate totals and verify constraints more precisely than free-form generation. MRP-VM and SOP Lang investigate workflow orchestration with state and acceptance conditions. S*LLM explores narrower language semantics and symbolic reasoning alongside LLMs; it is not presented as an established replacement for a general-purpose model.

Ploinky Wormhole explores communication between independently controlled environments. OpenDSU contributes questions of provenance, identity and rights across organizations. A signed result may establish origin or integrity under particular trust assumptions, but it does not prove that a scientific claim is true. Vector-symbolic and geometric approaches remain options to evaluate on specific tasks. The book’s final standard is practical: a person gives a Robot useful work, follows its progress and reviews a concrete result; the project preserves what is needed to do the work again.
