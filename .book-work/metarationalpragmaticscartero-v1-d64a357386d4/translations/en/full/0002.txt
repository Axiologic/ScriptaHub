An equivalence relation is reflexive, symmetric and transitive. Reflexivity requires every object to be equivalent to itself. Symmetry requires equivalence to work in both directions. Transitivity requires that if the first object is equivalent to the second and the second to the third, the first is equivalent to the third.
Such a relation divides the domain into disjoint classes called equivalence classes. The collection of classes is a partition. Grouping histories by the result R(h) automatically yields a partition: the same R value means the same class. A representation can therefore be understood as a way of specifying which differences we ignore.
One partition refines another when it separates some classes without merging elements already separated. For example, classifying documents by type and year refines classification by type alone. It can preserve old information and add new information. This does not mean it will automatically produce a better algorithm: it may increase cost and require more estimation data.
We will sometimes use the term “quotient space.” It denotes the set of equivalence classes, not a special geometric space. We replace each concrete history with the class of all histories considered equivalent. Geometry, if any, must subsequently be added through a distance or another structure.
Orders and Graphs
A partial order allows some pairs to be compared without requiring every pair to be comparable. An interpreter preserving event order and another preserving documentary sources may be incomparable: each conserves information the other ignores. There need not be a single sequence of representations from “bad” to “good.”
A graph consists of nodes and links. In MRP, nodes may be operations or results; links may represent dependencies. If a computation must first receive two results, the graph specifies that condition. A directed graph without cycles allows operations to be ordered so that each follows its dependencies. This is called a topological ordering.
A cycle is not necessarily an error. It may describe repeating an update until stabilization. But a rule must explain what repeats, which state changes and when the process stops. A circular drawing is not yet an executable algorithm.
Predicate and Invariant
A predicate is a property that can be true or false of an object within the chosen model. “Every event has an order index” is a predicate on a table. An invariant is a property that must remain true throughout an execution or a class of transformations.
For an MRP library, one possible invariant is that every accepted result preserves the identifiers of the sources used. This does not mean the sources are true; it means the result's origin is not lost. Another invariant may require an operation declared read-only not to modify external state.
A proof starts from assumptions and uses explicit rules to obtain a conclusion. A test executes one or more cases. A proof may cover every case in the model; a test does not acquire that power merely by being automated. In turn, a proof does not by itself check whether the model correctly describes the real world.
Cost and Size
A problem's size may be the number of events, the number of candidate interpreters or the maximum length of programs being searched. A linear procedure visits a number of elements proportional to the size. An exponential one may double the search space with every unit increase. These differences explain why a logically correct idea can be impractical.
Computability and complexity distinguish the existence of an algorithm from the resources needed to execute it. Introductory treatments of theoretical computer science develop this distinction systematically [

CHAPTER 03
Programs, Semantics, Interpretation
What Semantics Establishes
Syntax determines which expressions are well formed. Semantics determines how they are interpreted. In a programming language, it may describe state transitions, an execution's result or the properties commands preserve. Semantics must therefore not be reduced to a static dictionary of meanings. Abstract interpretation explicitly offers multiple semantics and relations between them [
Cousot1977
Consider a command that adds one to a number. Its semantics must specify whether the number is an unbounded mathematical integer or an integer represented by a fixed number of bits. At the maximum representable value, the answers may differ. Simply saying “it understands addition” conceals an essential modeling choice.
Operational semantics describes execution steps. Denotational semantics associates a program with a mathematical object describing its behavior. Axiomatic semantics expresses relationships between input conditions and output properties. These perspectives can complement one another. MRP does not replace them with a broader term; it treats them as tools available to the agent.
What Pragmatics Adds
A semantic rule does not always decide by itself whether it is worth applying, which information is missing or which goal must be satisfied. Here we introduce the pragmatic level: choosing the interpretation regime, relevant context and stopping criterion. Once chosen, the interpretation's rules must remain stable enough for verification.
We can call an interpretation whose domain and obligations are fixed for an execution “stabilized semantics.” This is a convention internal to the book, not a universally accepted classification in the philosophy of language. It enables a useful principle: the agent may change interpretation between revision episodes, but cannot tacitly change the meaning of rules in the middle of a proof.
For example, a system may switch from mathematical integers to 32-bit arithmetic. This is not merely an optimization if it changes results. It changes the model; old conclusions must be reexamined wherever the difference matters.
The Interpreter as an Object
In the proposed model, an interpreter receives input, context, goal and internal state. It produces a result, a new internal state and evidence. Here “evidence” will denote verifiable support: sources, tests, computational traces or proofs, rather than merely the agent's expressed conviction.
Interpret(input, context, goal, state) = (result, newState, evidence).
This expression is a conceptual interface, not a complete algorithm. Its fields must be restricted for each concrete interpreter. An order analyzer may require a table with unique indices. A verifier may require a formula in a precise logic. A generator may accept text, but its output will initially have proposal status.
Context must not become a place to hide unlimited information. If the selector can consult the full text while the baseline predictor receives only a summary, the comparison measures more than interpreter quality. Every experiment will declare exactly what each component can read.
Contracts and Composition
A contract specifies preconditions, promised results and permitted effects. Hoare-style logic expresses the relationship between a precondition, a command and a postcondition. Partial correctness says that if execution terminates and the precondition held, the postcondition holds; termination requires a separate obligation [
SoftwareFoundations
Consider an operation selecting a resource's last event. Its contract may require a nonempty history, a total ordering and unambiguous resource identification. The postcondition says the returned event belongs to the resource and is followed by no other event for that resource. This postcondition can be checked independently of how the operation was implemented.
Composing two interpreters requires more than matching formats. If the first returns “the last known event,” the second cannot assume “the last event that occurred in the world” without assuming the history is complete. This is an example of semantic incompatibility in an apparently technically correct interface.
Probabilistic interpreters require more cautious contracts. “It frequently produced correct answers” is not a universal logical postcondition. We can describe the tested domain, evaluation distribution and performance uncertainty. Composing probabilistic components does not turn those results into certainty.
Learning as an Interpreter
A learning procedure interprets data through a family of models and an adjustment criterion. It produces parameters, rules or programs. It can therefore be included in the same interface schema. Yet this does not make every operation identical: changing a temporary result differs from changing the library on which future tasks will depend.
We will separate working state from consolidated state. A new hypothesis can exist in an experimental branch without becoming an accepted rule. Promoting it requires tests and an explicit decision. This separation lets the agent explore without treating exploration as truth already acquired.
What Remains Stable
An architecture capable of modifying itself needs a core stable enough to determine which modifications have occurred. The core may be small: version management, execution rules, evidence types and cost accounting. It need not contain every domain concept in advance.
MRP becomes interesting if its core enables useful interpreters to develop without rewriting the entire system. Manually supplied components are legitimate, but must be declared separately from learned ones.
CHAPTER 04
Probability, Decision, Truth
Uncertainty Is Not Contradiction
An agent may not know whether access is available even when the real system has a precise state. An event may be missing, a source unreliable or the policy changed. Not knowing the state and a contradiction between two statements are different situations. The architecture must represent them separately.
A probability is a value between zero and one assigned to an outcome within a model. For mutually exclusive outcomes covering every possibility considered, probabilities sum to one. A distribution is the collection of these values. It describes the agent's uncertainty or a mechanism's regularity, depending on the model used.
The mean of a random variable is not the outcome that will necessarily occur. In a finite domain, it is the sum of possible outcomes multiplied by their probabilities. An unlikely outcome may still occur; a well-calibrated agent is not one whose individual predictions always come true.
Updating a Belief
Consider a fictional example: before a test, the agent assigns a probability of 0.2 to a fault being present. A signal occurs in 90% of faulty cases and 10% of cases without a fault. After the signal appears, the updated probability is 0.18 divided by 0.26, approximately 0.692.
The calculation compares two ways the signal could have appeared: 0.2 × 0.9 of cases arise from faults, while 0.8 × 0.1 do not. The new result is a conditional probability, not a proof. It depends on the correctness of the initial rates and their applicability to the current situation.
An MRP interpreter can perform this update. Another can challenge the model supplying the rates. Changing numbers within a model and changing the model are different operations; the second may require additional experience, rather than merely recalculating the first.
